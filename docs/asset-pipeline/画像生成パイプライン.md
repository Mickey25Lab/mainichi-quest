# 画像生成パイプライン

## 1. 文書の目的

この文書は、`mainichi-quest`の画像素材について、企画・デザイン確認から正式PNG、WebP最適化、正式WebP、`dist`配備、Preview、実機QA、mainへの反映までを一貫して定義する。対象は`01_vehicle`、`02_robot`、`03_super_robot`、`04_super_robot_equipped`、`05_equipment`、`06_medal`、`07_vehicle_logo_title`、`08_background`、`09_complete`。

全20車種を共通規格で管理し、コレクション詳細、報酬演出、シルエット、将来の追加車種に使える素材を整備する。車種ごとのCSSオフセットや特殊スケールへの依存を減らし、必要な位置・余白調整は原則として素材側で吸収する。

## 2. 基本原則と保存先

### 2-1. レビューと正式化を分ける

レビュー段階は20車種の一覧比較を中心に進める。正式PNGはレビューシートから切り出さず、**高解像度のデザイン修正済み素材**から生成する。未修正の元PNGに位置調整だけをかけて済ませない。

### 2-2. 正本と配信用を分ける

プロジェクトルートは`C:\Users\Kimihiko Sato\mainichi-quest`。方針資料・マスターCSV・命名規則・補助スクリプトは`docs/asset-pipeline/`、レビュー成果物は`review/collection/`に置く。

| 種類 | 保存先 | 役割 |
| --- | --- | --- |
| 正本PNG | `asset-source/collection/<category>/png/` | デザイン・配置・透明処理を確定した高解像度マスター。将来の再生成元。`dist`容量削減のために縮小しない |
| 正式WebP | `asset-source/collection/<category>/webp/` | 正本PNGから直接生成した、配信用条件適用済みの再生成可能な派生物 |
| dist用WebP | 例：`dist/assets/collection/01_vehicle/` | アプリが実際に読む配信物。正式WebPと同一バイトで置き、SHA-256一致を確認する |

### 2-3. WebP再圧縮の禁止

変換は必ず次の一方向とする。

    正式PNG → 必要なresize／encode → 正式WebP → 同一バイトでdistへ配置

**WebPを入力元にして新しいWebPを作らない。** `WebP → resize → WebP`、`WebP Q90 → WebP Q40`は禁止する。世代劣化を防ぎ、比較条件と再現性を揃えるため、各候補を正本PNGから直接生成する。

## 3. パイプライン全体像

    企画・デザイン確認
    → レビュー用候補
    → alphaクリーニング・機械的正規化
    → レビューシート・人間による視覚微調整
    → 高解像度の正式PNG・承認
    → WebP最適化条件の比較・FIX
    → 正本PNGから正式WebP生成
    → dist配備・SHA検証
    → Preview・実機QA
    → PR承認・mainへmerge

カラー正本FIX後、必要なカテゴリのシルエットを別工程で生成する。制作途中の素材を早まって`dist`へ配備しない。

## 4. 正式PNGまでの制作工程

### Phase 0：全体方針確認

対象カテゴリ、対象車種、参照するExcel・仕様書、レビュー範囲、今回実施しないことを先に確認する。目的が曖昧なまま生成・上書きを始めない。

### Phase 1：車種別修正方針の確認

対象カテゴリの修正指示を20車種すべてについて確認する。権利上避けたいマーク、色と識別性、既存デザインや本編との不一致、記号・番号の削除を確認し、指示のある車種はレビュー候補の段階で反映する。**このPhase 1から20車種のレビューシートを作り、指示の確認・デザイン候補・alpha前処理・機械的正規化・視覚微調整の各段階で更新して比較する。** Phase 5は初回作成の開始時点ではなく、正規化後の比較シートを整える工程である。

### Phase 2：レビュー用候補の作成

必要なデザイン変更を高解像度の候補画像に反映する。候補はまだ正式FIXではない。元PNGを変更せず、レビューシート切り出しを正式画像へ転用しない。

### Phase 3：前処理（alphaクリーニング）

透過する前景素材では、候補画像の**alpha < 16（0～255）**を完全透明化する。測定時だけ無視するのではなく、画像自体をクリーンにする。外接矩形・中心・足元の基準を安定させ、一覧・ポップアップ・シルエットでのずれを抑える。正式化時の高解像度生成物にも同じ処理を適用する。元PNGを無断で変更しない。不透明な背景には適用しない。

### Phase 4：機械的正規化

クリーン化後の非透過領域の外接矩形を取り、まず機械的に揃える。`01_vehicle`で採用した初期ルールは1254×1254 px、RGBA透過、左右余白110 px、下余白90 px、縦横等倍、横中央・下揃え。上余白は固定しないが上端をキャンバス外へ出さない。これは視覚調整の出発点であり、全カテゴリ共通の最終数値ではない。

### Phase 5：レビューシート生成

Phase 1から更新してきた一覧比較用レビューシートを、正規化後の状態に更新する。毎回20枚の個別PNGを納品しない。必要に応じて車種名、中央縦線、下揃え基準、外接矩形のオレンジ枠を表示する。オレンジ枠はalpha < 16除去後の実際の画像存在領域を示し、人の見た目と機械的領域の差を確認する。

### Phase 6：人間による視覚微調整

機械的正規化を土台に、20車種を横並びで見たときの占有感、中心、足元、余白を人の目で調整する。必要な車種だけ倍率・上下位置・左右位置を最小限修正する。`01_vehicle`では左右を確認したうえで主に倍率と上下位置を微調整した。数値の一致だけで見た目の統一感を判断しない。

### Phase 7：高解像度の正式PNG化

レビュー承認後、高解像度の元素材へデザイン修正、alphaクリーニング、承認済みの倍率・位置・余白を再適用して正式PNGを書き出す。**レビューシートの切り出し・拡大を正式PNGに使わない。** 正本PNGは将来の再生成元として高解像度を保つ。

### Phase 8：正式PNGレビュー

正式PNGから確認用シートを作り、承認した見た目、車種別修正、画質、透過、外接矩形、寸法を確認する。**人間がPNGを承認する前にWebPを量産しない。**

## 5. WebP最適化フェーズ

PNG承認後、用途とカテゴリごとに配信用条件を決める。候補はすべて**同じ正本PNGから直接生成**し、解像度、RGB Quality、Alpha Quality、ファイルサイズを記録する。見た目の差が分からない場合は容量とのバランスで判断する。

画像単体の100%表示だけで判断せず、実際の表示サイズで確認する。用途の例はコレクション一覧、問題画面、報酬ポップアップ、コレクション詳細、全画面背景。必要な用途だけを比較する。

**Step Aの解像度、Step BのRGB Quality、Step CのWebP alpha qualityを比較する際は、review配下に比較用Webページ（HTML）を作る。** 同一素材・同一表示サイズ・同一背景で候補を切り替え／横並び表示できるようにし、候補ごとの寸法、設定値、ファイルサイズを併記する。透過素材では薄い背景と実ゲームに近い背景も確認する。人間の画質判断と採用判断が済むまで、比較用WebPを正式WebPや`dist`へ置かない。

### Step A：解像度比較

実際のアプリ表示サイズを基準に比較する。透過前景の候補例は1254、896、768、640、480 px。必要に応じて他の候補も試す。元画像に近いほど良いと機械的に判断せず、実表示での見た目を優先する。正本PNGは縮小しない。

### Step B：RGB Quality比較

解像度FIX後、lossy WebPのRGB Qualityを比較する。候補例はQ90、Q80、Q70、Q60、Q50、Q40、Q30、Q20、Q10。必要な範囲を試し、候補Aから候補Bへ再圧縮しない。

### Step C：Alpha Quality比較

透過素材ではRGB Quality FIX後にWebP alpha qualityを比較する。**候補値の例は20／40／60／80**。必要なら20／60のように候補を絞って追加比較する。比較には基準画像（baseline）も含めるが、baselineはalpha qualityの数値ではない。外周、細線、半透明影、ローター、タイヤ、発光、透明境界を比較用Webページで実表示し、容量差も確認する。実際に比較する候補と採用値はカテゴリごとに記録する。不透明な素材では省く。これはPNG前処理の`alpha < 16 → 0`とは別の設定である。

### Step D：metadata確認

削除を前提にせず、正本PNGと生成WebPにEXIF、XMP、コメント、ICC profileがあるか調べる。なければ最適化として何もしない。ICCがある場合は、削除による色味の変化を別途比較して判断する。

## 6. カテゴリ別の採用条件を読むときの注意

比較中の候補、Kimiが採用した条件、現在`asset-source`や`dist`に置かれた実ファイルを区別する。各カテゴリの詳細は第15～17章にまとめる。`01_vehicle`の正式配信用条件は**640×640・RGB Q40・WebP alpha quality 60**である。

## 7. 正式WebP生成と検証

最適化条件FIX後、正本PNGから正式WebPを直接生成し、`asset-source/collection/<category>/webp/`へ保存する。全件についてファイル名対応、採用解像度、RGB・Alpha Quality、透過、正常デコード、欠損、件数、容量、実表示の見た目を確認する。既存の正式WebPと同名で置き換える場合は、対象と退避方針を確認してから実施する。

## 8. dist構造と配備

現在の主要な配信構造を次に示す。素材ごとの正式住所はアプリの参照先と照合する。

    dist/
    ├─ assets/
    │  ├─ collection/
    │  │  ├─ 01_vehicle/
    │  │  ├─ 02_robot/
    │  │  ├─ 03_super_robot/
    │  │  ├─ 04_super_robot_equipped/
    │  │  ├─ 05_equipment/
    │  │  └─ 09_complete/
    │  │     ├─ detail/
    │  │     └─ reward/
    │  ├─ backgrounds/
    │  │  ├─ vehicle/
    │  │  └─ collection/
    │  ├─ ui/
    │  └─ audio/
    └─ scripts/

旧`dist/answer/`と`dist/collection/`は廃止済みであり、新しい配備先に使わない。

正式WebP FIX後の配備順は次のとおり。

1. 正本PNGと最適化条件のFIXを確認する
2. 正本PNGから正式WebPを生成して`asset-source`側へ保存する
3. **同じWebPのバイト列**を正式な`dist`住所へ配置する
4. `asset-source`側と`dist`側のSHA-256を全件比較する（20車種なら20/20）
5. 件数、ファイル名対応、解像度、透過、デコードを全件確認する
6. Preview発行、実機QA、PR承認、main mergeへ進む

`dist`配置のために正式WebPを再エンコードしない。

### 8-1. 住所変更と画像変更を分ける

`dist`の住所変更では、**住所変更と画像内容変更を同じStepで行わない。**

1. 旧画像をバイト一致のまま新住所へ移し、参照パスだけ変更する
2. Previewで構造変更を確認する
3. 別PRで最適化・最新化した画像へ差し替える

パス変更と画像変更による不具合を切り分けるため、MOVE前後のSHA-256一致を必須とする。`asset-source`から`dist`への配備でも全件SHA-256一致を必須とする。

## 9. Preview・実機QA・main反映

`dist`反映後は必ずPreviewを発行する。Codexの機械テストだけで完了扱いにしない。Kimiが実機で表示、透過、サイズ感、画質、画像切れ、遷移、必要に応じて音を確認する。Kimiの`PR #XX OK`を受けてからmainへmergeする。画像制作や比較だけの段階では、Preview・Git操作・公開を先行させない。

## 10. シルエット生成

カラー正本FIX後、必要なカテゴリについて乗り物、ロボット、スーパーロボット、装備、メダルのシルエットを生成する。獲得済みはカラー、未獲得はシルエットで表示する用途を想定する。**カラー正本FIX前にシルエットを量産しない。**

## 11. `01_vehicle`で確立したレビュー運用

- レビュー段階では20車種の比較シート1枚を中心とし、個別PNG20枚は正式化後に作成した
- パトカーの`P → ★`、救急車・ヘリコプターの`赤十字 → ✱`、郵便車の色・封筒マーク・不要部品、F1カー・レーシングバイクの`01`除去を候補段階で確認した
- V8の視覚調整ではヘリコプター・飛行機を上へ浮かせた位置を採用した
- 後続の個別修正も含めた現行の正式PNGをWebPの入力元とする

この流れをrobot以降へ横展開し、余白、特殊形状、シルエット、アプリ上の見え方に差があればカテゴリ固有ルールを記録する。

## 13. 背景素材の扱い

背景は全画面表示のため、前景の解像度・Qを流用しない。`08_background`の実績と採用値は第16章に記録する。不透明な背景ではalpha threshold処理もWebP alpha quality比較も不要である。既存背景の世界観や構図を維持する。

## 14. 禁止事項と更新方針

- レビューシートを切り出して正式PNGに使わない
- 未修正の元PNGに位置調整だけをかけて正式化しない
- PNG承認前にWebPを量産しない
- WebPを再圧縮しない
- カラー正本FIX前にシルエットを量産しない
- 制作・比較段階で`dist`配備、Git操作、公開を混ぜない
- 住所変更と画像内容変更を同じStepで実施しない

`02_robot`以降で確立した規格、シルエット仕様、実装で分かった改善点、命名・保存フローを順次追記する。最終目的は、全20車種の素材を統一規格で再利用できる正式アセットとして整備し、承認済み配信物を再現可能な手順で届けることである。

## 15. `01_vehicle`：実績、比較値、現在の状態

以下の証拠パスはすべてプロジェクトルート（第2章）からの相対パス。**alpha threshold**はPNG画素の前処理、**WebP alpha quality**はWebPエンコード設定であり、同じ数値でも別工程である。

### 15-1. デザイン正式化・PNG

- デザイン指示は最新版`docs/asset-pipeline/マイクエ_キャラクター修正方針_V3.xlsx`の乗り物欄（C列）を車種ごとに確認する。実績としてパトカー`P→★`、救急車・ヘリコプター`赤十字→✱`、郵便車の色・封筒マークと不要部品、F1カー・レーシングバイクの`01`除去をレビューした。ブルドーザーは後続の再生成・3%拡大も反映した。
- V8までレビューシートで倍率・中心・足元を比較し、ヘリコプターと飛行機は上へ浮かせた配置を採用した。レビューシートから切り出さず、高解像度の修正済み個別素材へ確定値を再適用する。
- PNG前処理は`alpha < 16 → 0`。`alpha >= 16`の外接矩形を計測する。初期の機械的配置は1254×1254、左右110px、下90px、横中央・下揃え。その後の視覚調整が最終値に優先する。正式PNGは`asset-source/collection/01_vehicle/png/`に20枚、各1254×1254・RGBA・透明背景として存在する。
- 証拠：`review/collection/01_vehicle/`のV8レビュー・正式化前バックアップ、`asset-source/collection/01_vehicle/png/`。後続カテゴリへ左右110px／下90pxを無条件に流用しない。

### 15-2. WebP解像度・RGB Quality比較

| 項目 | 実施・採用・注意 |
| --- | --- |
| 入力・手順 | 正式PNGから各候補を直接生成。実際の表示サイズで見え方と容量を比較する。WebPからの再圧縮はしない |
| 解像度の検討値 | 1254、896、768、640（初回）、160、320、480、640（追加）。さらに480と640でQ違いの候補がある |
| 解像度の採用値 | **640×640**。480pxは比較候補であり、最終採用値ではない |
| RGB Qの検討値 | 480ではQ60／70／80／90を確認。640ではQ10／20／30／40／50／60／90を確認。両解像度にまたがる値を一括して「480で比較済み」と読まない |
| RGB Qの採用値 | **Q40**。640pxの正式WebPに適用済み |
| 証拠 | `review/collection/01_vehicle/dist_size_comparison/`、`dist_size_comparison_v2/`、`webp_quality_comparison/`、`webp_final_comparison/` |

比較候補の保存名だけで最終採用を断定しない。480px・Q60の2枚は比較候補であり、正式WebP20枚ではない。

### 15-3. WebP alpha quality・metadata・配備

- alpha qualityの初回比較は**20／40／60／80／baseline**、追加比較は**20／60／baseline**。証拠は`review/collection/01_vehicle/alpha_quality_comparison/`と`alpha_quality_extra_check/`。baselineは比較用の基準ファイル名であり、alpha qualityの数値として読まない。
- **採用alpha qualityは60**。`alpha_quality_comparison/alpha60/`のパトカー・クレーン車と、正式WebPのSHA-256が一致した。`alpha_quality_extra_check/alpha60/`のヘリコプターも一致した。
- PNGにEXIF／XMP／コメント／ICC profileがなく、`review/collection/01_vehicle/metadata_comparison/`のbaseline、metadata削除、ICCも削除した候補は比較した3車種でバイト一致。追加のmetadata最適化は不要だった。
- `asset-source/collection/01_vehicle/webp/`の正式WebPは20枚、640×640、lossy Q40・alpha quality 60。LANCZOS縮小・透過維持。`dist/assets/collection/01_vehicle/`の同名20枚と**20/20でSHA-256一致**した。

## 16. `08_background`：全画面・不透明背景の実績

### 16-1. デザイン・正式PNG

- 車種別デザイン修正は最新版Excelの背景欄（I列）を正とする。救急車とヘリコプターの`赤十字→✱`、郵便車のFUEL／GS除去と赤基調への調整、飛行機雲の向き修正を候補から最終PNGに反映した。指示のない車種の世界観・構図は維持する。
- 正式PNGは`asset-source/collection/08_background/png/`に20枚、各**1400×1050・RGB・透過なし**として存在する。候補と退避の証拠は`review/collection/08_background/i_column_candidates_2026-10-06/`、`final_png_staging_opaque_2026-10-06/`、`backup_before_i_column_2026-10-06/`。
- 不透明背景のため**alpha threshold処理もWebP alpha quality比較も不要**。透過前景の1254px、左右110px、下90pxを適用しない。

### 16-2. WebP比較・Q20採用

| 項目 | 実施・採用・注意 |
| --- | --- |
| 入力・出力 | 正式PNGを直接入力し、1400×1050を維持。リサイズ・トリミングなし、lossy WebP、不透明、不要metadataなし |
| ツール | Pillow **12.3.0**／libwebp **1.6.0**、`method=6`。各Qは同じ正本PNGから直接生成 |
| Q検討値 | 初回Q90／80／70／60／50／40、追加Q30／20／10／5。解像度比較はこの工程ではしていない |

## 18. 未実施カテゴリでの進め方

`04_super_robot_equipped`、`05_equipment`、`06_medal`、`07_vehicle_logo_title`、`09_complete`には、上記カテゴリの解像度、余白、Q、alpha qualityを**採用値として転記しない**。カテゴリごとに最新版Excelの対応列と正式素材を確認し、次の順に進める。

1. 20車種の元デザインと指示を1件ずつ照合し、必要なデザイン修正候補を作る。
2. 透過前景ならalpha thresholdの必要性を検証し、クリーン化後の外接矩形、中心、足元を計測する。不透明素材ならこの工程を省く。
3. 同条件の20車種レビューシートを作り、Kimiが視覚的な占有感・配置を承認する。サイズやY調整はカテゴリ固有に決めてパラメータを残す。
4. 承認済みの高解像度個別素材から正式PNGを生成し、20枚の寸法・透過・デザイン・名前・デコードを検証する。カラー正本承認前にシルエットを量産しない。
5. 正式PNGから直接、実用途に合う解像度候補を比較し、採用解像度でRGB Qを比較する。透過素材のみalpha qualityを比較する。各候補で解像度・Q・alpha quality・method・resampling・metadata・容量を記録する。
6. Kimiが採用条件を承認してから正式WebPを全件生成し、`asset-source`へ保存する。配備が必要な時のみ、同一バイトを`dist`へ置いて全件SHAを照合する。Previewと実機QAを経てPR／mergeへ進む。

各カテゴリの記録には**検討値／比較対象／採用値／判断理由／証拠パス／未実施項目**を同じセクションに置く。未確定の値は未確定と記す。
