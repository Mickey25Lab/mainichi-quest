# 変更別テストガイド

最終更新：2026-10-24  
対象：マイクエのすべてのPR

## このガイドの目的

変更ごとに必要な確認を必要な分だけ行い、Kimi が「何を見ればよいか」で迷わないようにする。すべてのPRで同じ量の実機確認を求めるものではない。

PRを出す人は、下の表から今回の変更に当てはまる行を選び、PR本文とKimiへの報告に確認内容を書く。複数の種類にまたがる場合は、そのすべてを行う。

## Kimiへの確認の伝え方

PRを報告するときは、必ず最初に **「あなたにしてほしいこと」** を置き、専門用語を使わずに次の4点を伝える。

1. 開く場所：Preview URL とQRコード、または読むMDの場所
2. 見ること：画面で確認できることを最大3つ
3. 見なくてよいこと：今回関係ない確認（例：アプリを遊ぶ必要はない）
4. 承認方法：問題なければ `PR #番号 OK` と返信してもらう

「差分を確認する」「CIを見る」「変更ファイル数を確認する」といった開発者向けの依頼をKimiへの確認項目にしない。自動確認の結果は、作業者が要約して報告する。

## 実行するテストの選び方

- 既存のテストに今回の変更と直接対応するものがあれば、必ず実行する。
- 対応するテストがない場合は、近い既存テストとPreviewでの最小操作を選び、PRに「専用テストがない」ことと理由を書く。
- UI・保存データ・導線に関係する変更では、PRの自動ブラウザスモーク結果を確認する。
- レイアウトに影響する変更では、PRのUI geometry audit結果を確認する。
- 保存データに関係する変更では、既存データを消さないことを確認するテストを必須にする。
- MDだけの変更では、アプリの動作テストを増やさない。その代わりリンクと表示の確認を行う。

## このガイド自身の変更

この文書を更新するPRでは、Markdownのリンクが解決できることと、VS CodeのMarkdownプレビューで表が読みやすいことを確認する。アプリの動作・保存データ・versionは変更しない。
